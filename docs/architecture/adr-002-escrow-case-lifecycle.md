# ADR-002: Escrow Case Identity and Lifecycle

Status: Accepted

## Decision

Protocol v2 will support multiple simultaneous escrow cases per account. Every case is identified by an immutable `bytes32 escrowId`.

The ID is generated by the escrow controller as:

```solidity
keccak256(
    abi.encode(
        block.chainid,
        address(this),
        escrowNonce,
        account,
        caseReferenceHash,
        amount
    )
)
```

The caller supplies an opaque `caseReferenceHash`, never legal narrative or personally identifying text.

## Stored case data

Each escrow case stores:

- `escrowId`
- source account
- amount
- opaque case reference hash
- optional supporting document hash
- creation timestamp
- optional expiry timestamp
- lifecycle state

No free-form legal basis, sanctions text, names, account numbers, or personal information may be stored in contract state or emitted in events.

## Lifecycle

Approved states are:

- `Active`
- `Released`
- `Burned`
- `Expired`
- `Cancelled`

Allowed transitions are:

- `Active -> Released`
- `Active -> Burned`
- `Active -> Cancelled`
- `Active -> Expired`

Terminal states cannot transition again.

## Expiry disposition

Expiry will not strand funds.

- An escrow with `expiry == 0` has no automatic expiry.
- After a dated escrow reaches expiry, anyone may call `expireEscrow(escrowId)`.
- Expiry changes the state to `Expired` and returns the escrowed amount to the original source account.
- A legal hold that must remain locked indefinitely must use `expiry == 0` and be resolved through governed release, burn, or cancellation.
- There is no grace period. The timestamp is the authoritative boundary.

## Release, burn, and cancellation authority

- Release requires the designated escrow-release role under governed permissioning.
- Burn requires a separate confiscation/burn role and dual-control governance assignment.
- Cancellation returns funds only to the original source account.
- Release may send funds to the source or another approved destination.
- Burn reduces total supply by exactly the escrowed amount.

## Accounting invariants

At all times:

- active case amount equals the amount reserved for that case
- per-account escrow total equals the sum of active cases for that account
- global escrow total equals the sum of all active cases
- total supply equals spendable balances plus escrowed balances
- terminal cases contribute zero to active escrow totals

## API and SDK decision

Protocol v2 APIs will address escrow operations by `escrowId`, not account address. Account-level queries return paginated case summaries.

The v1 account-based endpoints remain versioned under `/api/v1` during migration. New endpoints are introduced under `/api/v2`.
